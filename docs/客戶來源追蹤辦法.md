# 客戶來源追蹤辦法

更新日期：2026-08-16
適用範圍：EudTech 官網、Configurator、AI Agent 服務頁、開發信、廣告、詢價郵件、Microsoft Graph 事件服務、Firestore 與 Dataverse。

## 1. 目的

客戶來源追蹤必須回答四個不同問題：客戶第一次如何接觸 EudTech、最近一次由哪個有效管道回訪、哪一次接觸直接促成詢價，以及客戶自行表示如何得知 EudTech。四個答案分欄保存，不互相覆寫。

最終關聯必須形成可追溯鏈：`開發信或廣告活動 → 點擊／進站 → 瀏覽與表單事件 → quote_request_id → 詢價郵件 → Dataverse Event → 客戶來源結論`。

## 2. 判定原則

1. 客戶身分與客戶來源分開判定。姓名、學校、職稱、論文、研究領域及公開 Email 只能協助身分比對，不能單獨證明進站來源。
2. URL 參數只能表示來源聲明。開發信來源仍須以 Firestore 收件人索引及 Dataverse `OutreachSent` Event 雙重驗證。
3. 首次來源永久保留。直接回訪不能覆寫最近一次非直接來源。
4. 原始觸點採附加式紀錄。人工更正只能新增更正人、時間、原因及新結論，不能刪除原始證據。
5. 「未找到證據」記為 `direct_unknown`，不得改寫為搜尋、廣告、轉傳或開發信。

## 3. 已上線基線：後續更新不得退化

- 官網在瀏覽器保存 90 天的首次來源及最後有效來源。
- 保存 UTM、廣告 click ID、首次 landing page、目前 landing page、referrer、campaign ID、匿名 recipient source ID 及「如何得知我們」。
- 開發信連結使用匿名且不可逆的 recipient source ID，不在網址放置收件者 Email。
- Outlook 事件服務把來源資料寫入 `eudtrk_event.eudtrk_sourcepayload.customerSource`。
- 開發信判定同時核對 Firestore source index 與 Dataverse `OutreachSent` Event，並能區分本人詢價與轉寄／代詢。
- 第一方事件使用 UUID `eventId`，Netlify Blobs 以事件 ID 去重，避免重送重複計算。
- 目前資料基線為 3,816 位收件者、3,793 封唯一寄件、3,816 筆來源索引及 3,793 筆 Dataverse 寄件 Event，已驗證缺漏為 0。

正式證據：`/Users/serverc/WorkSpace-AI/deliverables/website-customer-source-attribution-20260816/IMPLEMENTATION_STATUS.md`。

## 4. 來源分類與證據層級

| 優先序 | 分類 | 成立條件 | 信心 |
|---:|---|---|---|
| 1 | `verified_outreach_email` | recipient source ID、campaign ID、Firestore 索引及 Dataverse `OutreachSent` Event 一致；可再核對 RFC Message-ID、寄件時間與 Outlook webLink | 已驗證 |
| 2 | `verified_paid_platform` | 平台 click ID 已由平台或伺服器驗證並與 conversion ID 關聯 | 高 |
| 3 | `attributed_utm_referrer` | UTM 或外部 referrer 完整，但沒有更高層證據 | 中 |
| 4 | `customer_self_reported` | 客戶在表單選擇或業務留下可追溯紀錄 | 客戶陳述 |
| 5 | `manual_review` | 多項證據衝突，等待具名人員處理 | 待確認 |
| 6 | `direct_unknown` | 沒有可驗證活動、click ID、UTM 或 referrer | 未知 |

高層級證據可提升結論，低層級資料不得覆寫高層級證據。衝突時保存全部原始值、衝突原因及最後裁決紀錄。

## 5. 必備資料欄位

每個可轉換事件至少保存：

- `event_id`、`event_name`、伺服器接收時間、瀏覽器事件時間。
- `visitor_id`、`session_id`、`quote_request_id`、匿名 `recipient_source_id`。
- first touch、last non-direct touch、conversion touch、customer self-report 四組來源。
- `source`、`medium`、`campaign`、`content`、`term`。
- `gclid`、`msclkid`、`fbclid`、`li_fat_id` 等實際存在的 click ID。
- first/current landing page、referrer domain、分享或轉介標記。
- 詢價 Email、Dataverse Matter/Event ID、RFC Message-ID、Outlook webLink。
- 證據狀態、信心等級、匹配方式、衝突原因。
- 人工更正的操作者、時間、理由、修正前與修正後內容。

## 6. 事件驅動資料流程

1. 瀏覽器產生帶 UUID 的第一方事件。
2. Netlify 第一方端點清理資料並寫入耐久事件帳本，同一 UUID 只接受一次。
3. 詢價提交沿用同一 `quote_request_id`，來源摘要進入詢價郵件與寄件日誌。
4. Microsoft Graph subscription 觸發 delta worker，不以固定掃描作為正式主流程。
5. worker 以 Firestore source index 及 Dataverse `OutreachSent` Event 驗證開發信來源。
6. worker 將原始來源、證據狀態及判定結果寫入 Dataverse Event source payload。
7. 對帳程序定期核對網站事件、詢價郵件、Firestore 與 Dataverse，缺件、重複及衝突均產生可追蹤異常事件。

## 7. 下一階段最強化要求

下列項目是後續開發契約，不代表目前已上線：

1. 由伺服器核發第一方 `visitor_id` 與 `session_id` Cookie，設定 Secure、SameSite=Lax 及明確有效期；來源 token 必須簽章並可驗證，防止自行竄改。
2. 建立附加式 touch ledger，逐筆保存進站、頁面、CTA、分享、表單開始及詢價提交，不只保留 localStorage 摘要。
3. 開發信先通過 EudTech 簽章轉址端點，記錄已驗證 click event 後再導向官網；轉址失敗時仍能安全抵達目標頁。
4. 使用單一 conversion ID 串起 page view、lead intent、quote submit、詢價郵件、Graph Event 與 Dataverse Event。
5. 在取得平台權限及同意後，將已驗證轉換以 offline conversion 方式回傳 Google Ads、Microsoft Ads、LinkedIn 或 Meta，並保存平台回執。
6. 建立明確的 consent、資料最小化、保存期限、刪除及匿名化程序；網址、公開報表及分析事件不得含原始 Email 或其他不必要個資。
7. 建立事件延遲、遺失、重複、簽章錯誤、對帳不一致及未知來源比例告警。
8. 產出只含彙總資料的來源成效報表，至少顯示各管道詢價數、已驗證轉換率、未知來源率及資料完整率。
9. 人工更正採 append-only 稽核紀錄；Dataverse 權限必須限制可更正角色。
10. 自然搜尋與 AI 搜尋應保存可取得的 referrer 與 landing page；無 referrer 時維持直接／未知，不依關鍵字或訪客身分猜測。

## 8. 驗收標準

- 相同 `event_id` 重送不增加筆數。
- 直接回訪不覆寫 last non-direct touch，任何回訪不覆寫 first touch。
- 偽造 recipient source ID、campaign ID 或簽章時，來源不得成為已驗證開發信。
- 開發信本人點擊、轉寄後第三人詢價、廣告 click ID、自然 referrer、自填來源及無來源六種情境均有自動測試。
- `quote_request_id` 能從官網事件一路讀回詢價郵件與 Dataverse Event。
- Firestore、OutreachSent Event、詢價 Event 對帳的 missing、duplicate、conflict 都必須為 0，或各自存在已追蹤異常事件。
- 報表不得輸出 UUID、原始 Email、完整 URL 查詢參數或 user agent。
- 正式發布前完成單元測試、端到端測試、Dataverse 讀回及正式站無測試詢價驗證。

## 9. 已知案例

- Shih-Hsin Wang：`verified_outreach_email`。2026-08-13 21:50:58 收到包含 Configurator 網址的開發信，約 37 分鐘後送出詢價；寄件 Message-ID、時間、主旨、Outlook 連結及 Dataverse 紀錄一致。
- 郭時聿：`direct_unknown`。沒有對應開發信、UTM、referrer、campaign ID 或廣告 click ID。姓名、論文、研究領域及公開 Email 只能證明可能身分與需求背景，不能證明進站來源。

## 10. 版本與發布

所有來源追蹤修改遵守 [開發中版本管理辦法](開發中版本管理辦法.md)：在 `codex/<更新名稱>` 開發分支完成、建立預覽並驗證，取得使用者明確核准後才合併及部署正式站。每次更新都要同步修訂本文件、測試及原始 prompt 保存紀錄。
