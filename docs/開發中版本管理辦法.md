# 開發中版本管理辦法

## 目的

本辦法規範 EudTech 官網每次更新從專案知識讀取、開發、預覽、核准、正式發布到回復的固定流程。

> 開發中版本與正式版本分離；只有使用者明確核准正式發布後，更新才能進入 `main` 與正式站。

## 專案知識讀取順序

任何人或 AI Agent 開始工作前，依下列順序讀取：

1. `PROJECT_STATUS.md`：目前 branch、production、已完成工作、待授權事項及接續順序。
2. 與本次功能相關的 Knowledge 文件，例如 `CONFIGURATOR_KNOWLEDGE.md`、`docs/網站資訊架構.md`、`docs/原廠內容與圖片來源.md`。
3. 本辦法：確認分支、預覽、核准、發布與回復規則。
4. 實際程式、測試與驗證腳本：以目前程式行為為準，不以舊截圖、舊報告或歷史 commit 推論現況。

若文件互相衝突，以較新的專案狀態、較具體的功能 Knowledge、實際程式與本辦法的正式發布限制共同判讀；不可自行放寬正式站發布條件。

## 最小版本結構

- `main`：正式站唯一來源，只保存已核准並已正式發布的內容。
- `codex/<更新名稱>`：每次更新建立一個短期分支，例如 `codex/update-ai-agent-page`。
- 預覽網址：每個更新分支對應獨立 Preview，不影響正式網域。
- 正式版本標籤：每次正式發布建立不可變 Git Tag，格式為 `vYYYY.MM.DD-NN`，例如 `v2026.08.19-01`。

不使用 `Dev`、`dev` 或長期 `develop` 分支作為新工作的來源。每次更新直接從最新 `main` 建立短期 `codex/*` 分支。

## 三種狀態

每次更新只能處於下列一種狀態：

1. `製作中`：正在修改或驗證，正式站維持不變。
2. `預覽待確認`：Preview 已可驗收，尚未取得正式發布核准。
3. `已正式發布`：使用者已明確核准，更新已進入 `main`、建立正式 Tag，並完成正式站讀回驗證。

「程式已完成」、「建置通過」、「Preview 可用」、「PR 已建立」與「已正式發布」是不同狀態，不得互相代替。

## 每次更新的固定流程

### 1. 建立更新版本

1. 回讀最新 `main` commit。
2. 從最新 `main` 建立 `codex/<更新名稱>`。
3. 將使用者原始指示保存於 `USER_ORIGINAL_PROMPTS.md` 或對應的專案知識文件；不得保存密碼、Token、憑證或個資。
4. 記錄本次更新範圍、驗收條件及不在範圍內的項目。
5. 狀態設為 `製作中`。

### 2. 開發與自動驗證

1. 所有修改只寫入本次 `codex/*` 分支。
2. 執行與風險相符的建置、功能、SEO、連結、表單、權限、資料契約及響應式驗證。
3. 有操作畫面的更新至少驗證桌面與手機；涉及深淺色或雙語時也必須覆蓋。
4. 驗證失敗時維持 `製作中`，不得提供正式發布建議。
5. `.github/workflows/development-policy-check.yml` 對 `codex/*` push 與指向 `main` 的 PR 執行：
   - PR 來源分支必須是 `codex/*`。
   - `npm run verify:original-prompts` 必須通過。
   - `npm run build` 必須通過。
   - Workflow 不執行正式部署。

### 3. 產生 Preview

驗證通過後產生獨立 Preview，狀態改為 `預覽待確認`。交付內容固定包含：

- Preview 網址
- 更新分支與 commit
- 修改內容
- 驗證結果
- 已知限制
- 預計正式版本號

Preview 不得取代、覆寫、重新部署或改變 `eudaemonia.tech` 的 production alias。

### 4. 使用者核准

只有使用者明確表示下列語意，才構成正式發布核准：

- 「正式發布」
- 「上線正式站」
- 「部署正式站」
- `DEPLOY PRODUCTION`

下列指示只代表繼續開發或完成 Preview，不構成正式發布核准：

- 「做」
- 「繼續」
- 「完成」
- 「做在網站上」
- 「更新官網」
- 「幫我最佳化」
- 對 Preview 內容提出修改或詢問

### 5. 正式發布

取得明確核准後，使用 `.github/workflows/promote-approved-preview-to-main.yml`，並提供：

- `source_branch`：必須是已驗收的 `codex/*` 分支。
- `commit_sha`：可選；未填時使用該分支最新 commit。
- `release_tag`：必須符合 `vYYYY.MM.DD-NN`。
- `approval`：必須輸入 `正式發布` 或 `DEPLOY PRODUCTION`。

Workflow 會強制：

1. 來源分支必須是 `codex/*`。
2. 指定 commit 必須存在於該來源分支。
3. `main` 到指定 commit 必須可 fast-forward，避免覆蓋正式歷史。
4. 原始指示驗證與 production build 必須通過。
5. 通過後才將指定 commit 推進 `main`，並建立不可變正式 Tag。

正式站由 `main` 的既有 production 部署流程發布。發布後必須讀回：

- production deploy 對應 commit
- 正式網址與主要路由
- 核心功能
- 手機版關鍵流程
- `build-meta.json` 或等效版本證據

正式發布回報固定包含：

- 正式網址
- 正式版本 Tag
- production commit
- 發布時間
- 驗證結果
- 上一個可回復版本

## GitHub 與部署保護

1. 禁止直接對 `main` 開發或提交功能修改。
2. 指向 `main` 的 PR 必須通過 `Development Policy Check`。
3. GitHub Repository Rules／Branch Protection 應設定：
   - 禁止 force push 與刪除 `main`。
   - 合併前要求 `Development Policy Check` 成功。
   - 限制可直接 push `main` 的角色，正式發布由 promotion workflow 執行。
4. GitHub Actions 原始碼可執行上述檢查與 promotion；Repository Rules 屬 GitHub 管理設定，必須在 repository settings 中持續保持啟用。
5. Netlify production 僅追蹤 `main`；`codex/*` 只能產生 branch deploy／Deploy Preview。

## 回復辦法

使用者要求「回復上一版」時，使用上一個已驗證的正式 Tag 重新發布，不刪除後續提交、分支、Tag 或歷史紀錄。

回復完成後必須讀回確認：

- production 已切換到指定正式版本
- 主要頁面可開啟
- 核心功能正常
- 問題版本不再承接正式流量
- `main`、正式 Tag 與 production deploy 的版本關係已記錄

## AI Agent 執行契約

任何 AI Agent 處理 EudTech 官網更新時，必須遵守本辦法。AI Agent 可以自行完成：

- 專案知識讀取
- `codex/*` 分支建立
- 程式修改
- 自動驗證
- Preview 部署
- PR 建立與驗收資料整理

AI Agent 未取得使用者明確正式發布核准前，不得：

- 將開發 commit 推入 `main`
- 執行 production promotion workflow
- 建立正式版本 Tag
- 部署或重新指向正式網域
- 將「做」、「繼續」或「完成」解讀為正式發布
