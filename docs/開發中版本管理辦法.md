# 開發中版本管理辦法
## 目的

本辦法規範 EudTech 官網每次更新從開發、預覽、核准、正式發布到回復的最小流程。核心原則是：

> 所有網站更新先合併至唯一上正式站前的測試分支 `codex/website-next-update`，完成整合驗收；只有使用者明確核准正式發布後，已驗收的版本才能進入 `main` 與正式站。

2026-10-04 使用者明確更正：「合併到 `codex/website-next-update` 才對 這才是唯一上正式站前的測試分支」。此更正優先於舊版文件中將各功能分支預覽視為最終驗收入口的說明。

## 最小版本結構

- `main`：正式站唯一來源，只保存已核准並已正式發布的內容。
- `codex/website-next-update`：唯一上正式站前的整合測試分支，收納各項更新並作為正式發布前的驗收來源。
- `codex/<更新名稱>`：可用於隔離個別功能的短期工作分支；完成後合併至 `codex/website-next-update`。
- 唯一正式驗收測試網址：`https://codex-website-next-update--website-eudtech.netlify.app/`。
- 功能分支、PR、歷史部署或本機預覽只作開發輔助，不取代上述整合測試站，也不代表其內容已整合。
- 正式版本標籤：每次正式發布建立不可變 Git Tag，格式為 `vYYYY.MM.DD-NN`，例如 `v2026.08.16-01`。

不另設 `develop`、`dev` 或 `QA` 作為正式發布前的第二套驗收流程。短期工作分支可以從最新 `main` 建立，但交付前必須合併至 `codex/website-next-update` 並驗證整合結果。

## 分支切分原則

- 使用者每次提出一項網站修改，就建立一個獨立更新分支；修改只有一個字元時也適用。
- 使用者在同一句指示中要求的多項修改，視為同一批更新並放在同一分支。
- 使用者針對同一預覽版本指出錯誤、跑版或功能不正常時，修正留在原分支，直到該預覽版本可再次確認。
- 每個更新分支保存提交紀錄並執行驗證；完成後合併至 `codex/website-next-update`，保留測試分支上其他已整合的更新。
- 同一測試版本的後續修正持續更新 `codex/website-next-update`，對外固定提供同一個驗收網址。
- 準備正式發布時，以使用者已明確核准的整合測試版本為來源，核對該版本實際包含的更新範圍。

分支用來隔離每項修改；commit 用來保存該分支內每次修正；`codex/website-next-update` 的部署用來提供可操作、可觀察的整合驗收版本。

## 三種狀態

每次更新只能處於下列一種狀態：

1. `製作中`：正在修改或驗證，正式站維持不變。
2. `預覽待確認`：更新已合併至 `codex/website-next-update`，統一測試網址已部署且通過整合驗證，尚未取得正式發布核准。
3. `已正式發布`：使用者已明確核准，更新已合併至 `main` 並完成正式站讀回驗證。

「程式已完成」、「建置通過」、「預覽可用」、「已合併」與「已正式發布」是不同狀態，不得互相代替。

## 每次更新的固定流程

### 1. 建立更新版本

1. 讀取最新 `main` 與 `codex/website-next-update`，確認正式版與已整合更新的範圍。
2. 建立 `codex/<更新名稱>` 分支。
3. 保存使用者原始指示。
4. 記錄本次更新範圍、驗收條件及不在範圍內的項目。

### 2. 開發與自動驗證

1. 在短期工作分支開發；整合與修正的目標為 `codex/website-next-update`。
2. 執行與變更風險相符的建置、功能、SEO、連結、表單及響應式驗證。
3. 有操作畫面的更新必須驗證電腦版與手機版。
4. 驗證失敗時維持 `製作中`，不得提供正式發布建議。

### 3. 產生預覽版本

功能驗證通過後，將更新合併至 `codex/website-next-update`，部署統一測試網址，再驗證本次功能與既有整合內容；全部通過後，狀態改為 `預覽待確認`。推送前須確認遠端分支是否有其他更新；有更新時先整合，不得強制覆蓋。交付內容固定包含：

- 統一測試網址及對應 commit
- 修改內容
- 驗證結果
- 已知限制
- 預計正式版本號

預覽版本不得取代、覆寫或重新部署正式站。

### 4. 使用者上線判定

正式上線由使用者自行判定。使用者是否滿意、是否仍有設計想法，以及該版本能否正式上線，是三項分開處理的狀態。

只有使用者明確表示「這版可以上線」、「驗收通過」、「正式發布」、「上線」、「部署正式站」或語意完全相同的指示，才構成正式發布核准。取得正式發布核准後，AI Agent 必須依正式發布流程立即部署，不等待其他設計想法。

使用者明確表示「這版不能上線」時，該更新分支維持 `製作中` 或 `預覽待確認`，並依使用者指出的問題繼續修正。

「做」、「繼續」、「完成」、「做在網站上」、「幫我優化」及對預覽內容的討論，不構成正式發布核准。

使用者提出意見但未明確表示能否上線時，AI Agent 不得自行推定正式發布核准或拒絕；正式站保持不變。

### 5. 正式發布

取得核准後：

1. 確認使用者核准的是 `codex/website-next-update` 的哪個已驗收 commit，以及該版本包含的更新範圍。
2. 將核准的整合測試版本合併至 `main`；若測試分支已有後續未核准提交，不得一併發布。
3. 由正式部署流程發布 `main`。
4. 建立 `vYYYY.MM.DD-NN` 正式版本標籤。
5. 讀回正式網站的版本、主要頁面、核心功能及行動版結果。
6. 將狀態改為 `已正式發布`。

正式發布回報固定包含：

- 正式網址
- 正式版本號
- 發布時間
- 驗證結果
- 上一個可回復版本

## 回復辦法

使用者要求「回復上一版」時，重新部署上一個已驗證的正式版本標籤。回復不刪除後續提交、分支、標籤或歷史紀錄。

回復完成後必須讀回正式站，確認：

- 正式版本已切換
- 主要頁面可開啟
- 核心功能正常
- 上一個問題版本不再提供正式流量

## AI Agent 執行契約

任何 AI Agent 處理 EudTech 官網更新時，必須遵守本辦法。AI Agent 可以自行完成工作分支建立、程式修改、自動驗證、合併至 `codex/website-next-update` 及統一測試站部署；必須以該測試分支提供正式發布前的驗收，不能以功能分支預覽取代；AI Agent 未取得使用者的明確正式發布核准前，不得合併 `main`、建立正式版本標籤或部署正式站。
